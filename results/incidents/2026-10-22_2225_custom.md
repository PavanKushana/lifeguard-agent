## Root cause

The cron job 'collect-debug-logs' added on 2026-10-20 writes unbounded API debug dumps to /var/log/shop/debug.log, which grew to 17.5 GB and filled the root filesystem (97% used), causing log writes to fail with ENOSPC and returning 500 errors for dynamic requests.

Confidence: high. Evidence:
- API logs show repeated 'failed to write log entry: No space left on device' errors starting 2026-10-22 22:10:19
- Root filesystem / is 97% used (29.1G used, 0.9G free) per check_disk
- /var/log/shop/debug.log alone consumes 17.5G per check_folder_sizes
- Recent changes show 'collect-debug-logs' cron job added 2026-10-20 22:25:19 writing to that exact file

## Fix

**Disable cron job and move debug log to PostgreSQL volume**

1. `disable_job(job=collect-debug-logs)`
2. `move_files(from_path=/var/log/shop/debug.log, to_mount=/var/lib/postgresql)`
3. `restart(container=api)`

How to undo: Re-enable the cron job (systemctl enable collect-debug-logs) and move the log file back if needed

What was done:
- turned off the job collect-debug-logs
- moved /var/log/shop/debug.log (17.5 GB) to /var/lib/postgresql/moved-files/ on /var/lib/postgresql
- restarted api

Options that were offered:
- Disable cron job and move debug log to PostgreSQL volume (recommended) (approved)
- Move debug log to PostgreSQL volume only (keep cron job)

## Follow-ups

- Risk of the chosen fix: Debug logging feature is lost until a rotated-log solution is implemented
- Long-term fix suggested by the investigator: Implement log rotation for /var/log/shop/debug.log (using logrotate) with size limits, reduce the verbosity of the debug dump, or configure the cron job to write to a separate volume with adequate capacity. Monitor disk usage and set alerts for filesystem usage thresholds.
