## Root cause

The API version 2.3.2 introduced a Lua script that triggers a segmentation fault in Redis 7.4, causing the cache container to crash (SIGSEGV). The API has since been rolled back to 2.3.1, but the cache container remains down, causing the API health check to return HTTP 503.

Confidence: high. Evidence:
- list_containers shows cache exited with code 139 (SIGSEGV) 23 seconds ago
- get_logs cache contains a Redis bug report ending with 'Suspect RAM error? Use redis-server --test-memory'
- get_logs api shows 'cache unreachable' errors and HTTP 503 responses after the cache crash
- recent_changes records API 2.3.2 deployed at 00:30, rolled back to 2.3.1 at 00:36:26, cache crash at ~00:38:58
- search_past_incidents matches a prior incident where API 2.3.2's Lua script caused Redis segfault, fixed by rolling back API to 2.3.1

## Follow-ups

- Risk of the chosen fix: If the Lua script from 2.3.2 left Redis in a corrupted state, restart might not help (but past incident shows it does)
- Risk of the chosen fix: Does not address underlying Redis 7.4 Lua bug; future API upgrades could retrigger it
- Long-term fix suggested by the investigator: Either pin the cache service to a known‑stable Redis version (e.g., `redis:7.2-alpine`) or modify the API’s Lua script to avoid patterns that trigger the Redis 7.4 segfault, test the change in staging, then redeploy. Monitor Redis logs for crashes after any version change.
