## Root cause

The Redis cache container (version 7.4.0) crashed due to a segmentation fault (signal 11), causing the API to lose cache connectivity and return 500 errors for login and cart endpoints.

Confidence: high. Evidence:
- Cache container status shows Exited (139) 25 minutes ago
- Cache logs show Redis 7.4.0 crashed by signal 11 at 2026-10-22 23:38:06
- API logs show Error 111 connecting to cache starting at 2026-10-22 23:39:06, leading to 500 errors for /api/login and /api/cart
- Recent changes show cache upgraded from redis 7.2 to 7.4 nine days ago

## Fix

**Restart cache container (keep upgrade)**

1. `restart(container=cache)`

How to undo: No undo needed; container remains on redis:7.4

What was done:
- restarted cache

Options that were offered:
- Restart cache container (keep upgrade) (approved)
- BLOCKED by the safety check: Rollback cache to redis:7.2 (step 1: cache holds data and has run redis:7.4 for 9 days; its data files are in that version's format, and redis:7.2 may not be able to read them. Only an upgrade from the last day can be rolled back)

## Follow-ups

- Risk of the chosen fix: High likelihood of immediate re-crash due to known segmentation fault bug in 7.4.0
- Risk of the chosen fix: Does not address root cause; users will be impacted again if cache crashes
- Long-term fix suggested by the investigator: Pin the cache to a known‑stable Redis version (e.g., `7.2` or a later patch release) and test any version upgrades in a staging environment before deploying to production. Consider enabling Redis crash‑dump collection and monitoring for segmentation faults to catch similar issues early.
