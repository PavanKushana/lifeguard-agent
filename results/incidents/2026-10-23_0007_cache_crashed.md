## Root cause

The cache container (Redis 7.4) crashed due to a known SIGSEGV bug (signal 11) after being upgraded from Redis 7.2 nine days ago, causing the API to fail connecting to cache and return 500/503 errors for login, cart, and health endpoints.

Confidence: high. Evidence:
- Cache container shows Exited (139) 25 minutes ago (list_containers)
- Cache logs show Redis 7.4.0 crashed by signal 11 at 2026-10-22 23:42:32 (get_logs cache)
- API logs show Error 111 connecting to cache:6379 starting at 2026-10-22 23:43:32 (get_logs api)
- Recent changes show cache upgraded from redis 7.2 to 7.4 nine days ago (recent_changes)

## Fix

**Restart cache container (keeps Redis 7.4)**

1. `restart(container=cache)`

How to undo: No undo needed; container runs same image

What was done:
- restarted cache

Options that were offered:
- Restart cache container (keeps Redis 7.4) (approved)
- BLOCKED by the safety check: Rollback cache to Redis 7.2 (step 1: cache holds data and has run redis:7.4 for 9 days; its data files are in that version's format, and redis:7.2 may not be able to read them. Only an upgrade from the last day can be rolled back)

## Follow-ups

- Risk of the chosen fix: Redis 7.4 bug will likely cause another crash, leading to repeated outages
- Risk of the chosen fix: Does not address root cause
- Long-term fix suggested by the investigator: Pin the cache service to a known‑stable Redis version (e.g., `redis:7.2` or a later patch release that resolves the SIGSEGV bug), monitor Redis logs for crashes, and test upgrades in a staging environment before applying to production.
