## Root cause

The Redis 7.4 container crashed with a segmentation fault (signal 11) 25 minutes ago, leaving the session store unavailable. The crash is a known bug in Redis 7.4.0 triggered after the upgrade from 7.2 nine days ago.

Confidence: high. Evidence:
- list_containers: cache container status 'Exited (139) 25 minutes ago'
- get_logs cache: 'Redis 7.4.0 crashed by signal: 11' bug report
- recent_changes: 'Upgraded cache from redis 7.2 to 7.4' 9 days ago
- check_endpoint api/health: HTTP 503 indicating API cannot function without cache

## Fix

**Restart cache and increase memory limit (keep Redis 7.4)**

1. `restart(container=cache)`
2. `set_memory_limit(container=cache, memory_mb=512)`

How to undo: Restart cache and set_memory_limit back to 256 MB

What was done:
- restarted cache
- set the memory limit of cache to 512 MB

Options that were offered:
- Restart cache and increase memory limit (keep Redis 7.4) (approved)
- BLOCKED by the safety check: Rollback cache to Redis 7.2 (step 1: cache holds data and has run redis:7.4 for 9 days; its data files are in that version's format, and redis:7.2 may not be able to read them. Only an upgrade from the last day can be rolled back)

## Follow-ups

- Risk of the chosen fix: Segfault bug in Redis 7.4.0 will likely crash again (signal 11 is code defect, not OOM)
- Risk of the chosen fix: Increases cache memory limit to 512 MB (total container limits become 2304 MB, still under 8192 MB)
- Risk of the chosen fix: No guarantee of stability; users may see repeated outages
- Long-term fix suggested by the investigator: Test Redis upgrades in a staging environment, enable health‑check/restart policies, and monitor container logs for crashes before deploying to production.
